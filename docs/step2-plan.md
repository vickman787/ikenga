## 1. Goal and what "done" means

### Goal

Turn the Step 1 skeleton into a product that actually moves money on Celo mainnet, in the exact way the two tracks require:

1. A customer pays $1 (USDT) into `JobEscrow` on Celo mainnet; accept releases to the vault, reject refunds + bond.
2. Agents pay for their own tools per call via x402 through Celo's facilitator — real verify + settle, real tx hashes.
3. The naira leg converts USDT → cNGN on Textile FX (firm RFQ quote, single on-chain swap), and the cNGN is sent to a **named real supplier's** wallet.
4. The CFO serves or pays an agent **only after** that agent's Self Agent ID verifies — on-chain, via the official SDK or a direct registry read. No verified identity, no payment, no service.
5. Every counted transaction carries the ERC-8021 attribution tag, and the agent is registered on ERC-8004.
6. Every CFO decision is recorded in the hash-chained ledger, with the tx hash attached, and the log is publicly verifiable.

## 2. Per-workstream plan

### 2.0 Cross-cutting: one chokepoint for all transactions

**Files:** new `packages/payments/src/send.ts` (+ `packages/payments/src/attribution.ts`); used by every workstream below.

- All outbound transactions go through one function, `sendTagged()`, which (a) attaches the CIP-64 `feeCurrency` (stablecoin gas — see risk R-9, unverified for Foundry; use viem for this path), and (b) appends the ERC-8021 attribution suffix via `@celo/attribution-tags` (`withAttribution(code)` / `toDataSuffix(code)`). Nothing else in the repo broadcasts a transaction.
- **Attribution tag — verified facts:** format is `celo_` + 12 hex chars; Schema 0 suffix is `[calldata] + [codes] + [codesLength 1 byte] + [schemaId 0x00] + [magic 16 bytes 0x8021…]`; the EVM discards trailing bytes, so execution semantics do not change. Tagging itself is open, but **credit is gated at the registry/indexer layer**: the hackathon assigns the code at registration, and a self-derived code will silently never be credited. Sources: https://docs.celo.org/build/agents/attribution-tags, https://github.com/celo-org/attribution-tags (BUILDERS.md).
- **Critical, verified:** x402 settlements on Celo **carry no tag today** — the facilitator submits the settlement tx, not your wallet, and Schema 2 (role-based tagging, facilitator adds its own `w`) is "under review upstream in x402-rs/x402-rs#99" and not live. Declaring the app code in `402` responses via `declareBuilderCodeExtension` (`@x402/extensions`) is harmless now and picked up automatically once live, but **do not count on x402 settlement txs being tagged**. Tag the agent's own transactions instead: ERC-8004 registration, Textile approval + swap, cNGN payout, escrow/vault calls. Sources: https://github.com/celo-org/attribution-tags (BUILDERS.md).
- **Tests first:** unit tests for `sendTagged()` — tag is appended and parseable by `fromDataSuffix`, original calldata is unchanged, no-tag path throws, duplicate-tag merge behaviour. Live test: one small tagged tx on Sepolia, verified with `verifyTx`.

### 2.1 Workstream A — Real x402 settlement via the Celo facilitator

**Verified facts (sources: https://x402.celo.org/SKILL.md, https://docs.celo.org/build/agents/x402)**

- Facilitator API is **`https://api.x402.celo.org`** (mainnet) and **`https://api.x402.sepolia.celo.org`** (testnet). `https://x402.celo.org` is the **dashboard only** — do not point a resource server at it.
- Network `eip155:42220` (mainnet), `eip155:11142220` (Sepolia). Scheme `exact` only.
- **Only `/settle` requires an API key** (`X-API-Key` header). `/verify` and `/supported` are open. The key is created by a human on the dashboard: connect an EVM wallet, Create API key, sign a message (no gas); key looks like `x402_…`, shown once. Sign in with GitHub → mainnet free credits; Skip → testnet credits only, GitHub cannot be added later. New accounts start with free credits (one per settlement); after those, deposit USDC on the dashboard. Pricing: **gas at cost + 0.3% of payment value**, or gas only when the asset has no USD price (always wARS/wMXN/wPEN/wCLP; while feed stale: wBRL, wCOP, **cNGN** — check `feeApplies` on each `paymentAssets` entry). Out of credits/balance → `/settle` returns `402 insufficient_credits`.
- Supported mainnet assets (10): USDC, USDT, USAT (EIP-3009, 6 decimals), wARS, wBRL, wMXN, wCOP, wPEN, wCLP, **cNGN** (Permit2, 6 decimals for cNGN, 18 for the wFIAT tokens). **Testnet supports USDC only.** USDT mainnet `0x48065fbBE25f71C9282ddf5e1cD6D6A887483D5e`, `extra.name = "Tether USD"`, `extra.version = "1"` — the EIP-712 domain name is **not** the symbol; using the symbol fails verification. cNGN `0xF6829D7393dAe24509eb1E52eE8e572e2E271a4f`, Permit2, 6 decimals.
- **cNGN is the exception for gas sponsoring:** Permit2 assets normally get EIP-2612 gas sponsoring **only if** the seller's route declares `extensions.eip2612GasSponsoring`; cNGN has **no EIP-2612 `permit()`**, so do NOT declare it for cNGN. A first-time cNGN payer must send `approve(Permit2, amount)` on the cNGN contract themselves and pay that gas; after that, payments are signature-only until the allowance runs out. Permit2 canonical address: `0x000000000022D473030F116dDEE9F6B43aC78BA3`.
- **Do not hand-build `/verify`/`/settle` payloads.** The Celo SKILL.md says explicitly to use the middleware. Use `@x402/hono` (or `@x402/express`), `@x402/core`, `@x402/evm` — verified against `@x402/*@2.23`, with `@x402/evm` **2.26.0** (2026-09-15) adding USDT/USAT to the Celo mainnet default-asset table. Buyer side: `@x402/fetch` + `@x402/evm` + `viem`. **UNVERIFIED:** a pinned "use version X" beyond 2.23/2.26.0; re-check installed versions against npm at build time.
- Flow: client requests route with no payment → middleware returns **402** with the requirements in the base64 `payment-required` header → client signs EIP-3009 authorization (or Permit2 transfer) and retries with the payment header → middleware calls facilitator `/verify` then `/settle` (with `X-API-Key`) → facilitator submits the on-chain transfer, pays gas, returns after 1 confirmation. Settlement latency measured p50 1,627–1,651 ms, p95 ~2.7 s; settlements run one at a time per network, so 2–3.5 s end-to-end is typical.
- **UNVERIFIED / discrepancies to resolve at build time:** (a) the retry header is `X-PAYMENT` in the v2 SKILL.md but `PAYMENT-SIGNATURE` in Celo docs — trust `X-PAYMENT` (v2) but verify against the installed middleware; (b) the exact facilitator `/verify`/`/settle` JSON envelopes are not published — do not assert a hand-built shape; (c) no documented HTTP client timeout exists in the Celo docs — pick one (e.g. 30 s, as used in the Coven x402 work) and label it a choice, not a sourced fact. Two payments from the same wallet within seconds can race on the permit nonce and answer `402` once — retry.
- Gotchas from the SKILL.md: do not use legacy `x402-express`/`x402-fetch` or the v1 `paymentMiddleware(payTo, routes, facilitator)` shape; do not use a bare dollar price `"$0.01"` (silently resolves to USDC); Permit2 assets need `assetTransferMethod: "permit2"` in `extra`; buyer spend controls must be set via `client.setSpendControls(...)` (not the constructor — silently ignored), default cap `"$1"` per payment for USDC/USDT/USAT, opt in to Permit2 assets via `spendControls.allowedAssets`; forgetting `createAuthHeaders` → `401` on settle; `payTo` is the seller's wallet, never the facilitator.
- **CIP-64 feeCurrency** is a separate mechanism for the agent's **own** transactions (not x402 settlement, where the facilitator pays gas): a Celo tx can name an ERC-20 as `feeCurrency` so an agent holding only stablecoin never needs CELO. `viem` supports it natively; `cast` does not expose it. **UNVERIFIED:** the full `feeCurrency` allowlist — one skill says cUSD/cEUR/USDT, Celo docs say USDC/USDT. Check the on-chain `FeeCurrencyDirectory` before asserting a list.

### 2.2 Workstream B — Textile FX RFQ quote + swap USDT ↔ cNGN

**Verified facts (sources: https://docs.textilecredit.com/ and sub-pages listed above)**

- Textile FX is an **RFQ venue, not an AMM**: you name a size, independent makers ("fillers") price it, the swap clears in a single on-chain transaction. Settlement uses Textile's own deployments of the UniswapX `LimitOrderReactor` v2.1.0.
- **Celo (42220) live corridors:** cNGN ↔ USDT, wARS, wBRL, wMXN, wCOP, COPM, IDRX, VGBP, VCHF, G$, cNGN ↔ G$, USAT, USDC, CELO, WETH — all vs USDT. USDT `0x48065fbBE25f71C9282ddf5e1cD6D6A887483D5e` (6 dp), cNGN `0xF6829D7393dAe24509eb1E52eE8e572e2E271a4f` (6 dp). **LimitOrderReactor (Celo) `0xa9AA0a64769cBed4d3B1Ceb4Df01CdE915C235b3`** — matches Step 1 constants. Fee controller `0x356f4FBe18893997D2F893AE8860eD6060b4521d`, **0.02% / 2 bps taker fee, charged in the sell token, already inside the quoted rate** (`feeAmount` is inside `takerPays`). Permit2 canonical `0x000000000022D473030F116dDEE9F6B43aC78BA3`.
- **RFQ API v2, base `https://api.textilecredit.com/v2`** (no official TS/JS SDK found in any doc read — integration is REST + viem; OpenAPI at https://docs.textilecredit.com/openapi-v2.json, also `GET /v2/openapi.json`; Postman collection at https://docs.textilecredit.com/textile-fx.postman_collection.json; public rates feed `GET https://api.textilecredit.com/tickers`). **UNVERIFIED:** whether an npm `@textile/*` package exists — do not assume one; plan on raw `fetch` + viem.
- Endpoints: `POST /v2/rfq/preview` (indicative, free, no `taker`, no credential — **not a promise**, firm price can differ); `GET /v2/rfq/levels?chainId=<id>` (price ladder, min/max sell amount, up to 9 points per pair, cached ~2 s); `POST /v2/rfq/request` (firm quote, **blocks** while makers answer); `POST /v2/rfq/{id}/submit` (`{txHash}`, idempotent on same hash, 409 on a different hash); `GET /v2/rfq/{id}` (status; **never replays `encodedOrder`/`signature` or the claim token — store them from the `request` response**); `POST /v2/rfq/{id}/cancel` (releases maker inventory only while `quoted`; does not un-sign the order and does not free the outstanding-RFQ slot).
- `POST /v2/rfq/request` body (exactly one of `sellAmount`/`buyAmount`): `{chainId: 42220, sellToken, buyToken, sellAmount: "<atomic units as string>", taker: "<wallet>", takerProof: {nonce, issuedAt, signature}}`. Amounts are strings in atomic units; rates are RAY-scaled (1e27) strings; timestamps ISO-8601 UTC. `sellAmount` = exact-input, **gross fee-inclusive spend cap**; `buyAmount` = exact-output. Optional `preferredLiquidityWallets` / `restrictedLiquidityWallets` (max 10 each, mutually exclusive) and `includeAttribution: true` (+ up to 3 `builderCodes`, 1–32 chars `[a-z0-9_]`, `textile_`/`tp_` reserved) which appends an ERC-8021 tag to `transactions.swap.data`.
- Response: `data.rfqId` (`rfq_…`), `data.claimToken` (`rfqc_…`, returned **exactly once**), `data.status: "quoted"`, `data.quote` with `sellAmount`, `buyAmount`, `feeAmount`, **`takerPays` (exactly what leaves the wallet — approve this, not `sellAmount`)**, `rateRay`, `expiresAt` (accept cutoff, can be sooner than the 60 s cap), `orderDeadline`, `latestOrderDeadline`, `reactor`, `taker`, `encodedOrder`, `signature`, `orders[]`, plus `data.transactions.approval` and `data.transactions.swap` (`{to, data, value: "0", chainId}`), and `data.routing`. **No-quote is HTTP 200**, not an error: `data.status: "no_quote"`, `reason` in `no_makers_online` / `no_restricted_liquidity` / `no_valid_quote`, plus `availableSellAmount`/`availableBuyAmount` and, when another quote holds the liquidity, `reservedUntil`/`retryAfterMs`.
- **Auth, two modes:** (1) Partner API key (created in the app): `Authorization: Bearer <key>` — replaces the wallet signature entirely, never send `takerProof` with a key. Gives its own rate-limit budget, webhooks, partner-scoped RFQ ownership. (2) **Keyless (wallet-only):** first firm request carries `takerProof` — an EIP-712 signature by the taker wallet over domain `{name: "Textile Taker Control", version: "1", chainId}`, type `TakerControl {taker, chainId, nonce: bytes32, issuedAt: uint256}` (v2 "Textile Proof of Funds" variant also accepted; `scheme: "eip191"` personal_sign for hardware wallets). `issuedAt` must be within 60 s of their clock (5 min for eip191). One verified proof earns a grant covering that wallet+chain for ~12 h; after that, `401 proof_of_control_required` tells you to sign again. Preview never needs a proof. Cancel/submit/status need RFQ ownership: `X-Rfq-Claim` header (claim token) or the API key that requested it; anything else is 404.
- **Proof of funds:** a firm request checks the taker's on-chain sell-token balance (exact-input checked before makers are woken, against the gross cap). Live quotes reserve their spend: `balance ≥ committed + required`. Shortfall is `400 insufficient_funds` with `required`/`available`/`committed`. Only balance is checked, not allowance.
- **Timing / limits:** reply budget 750 ms default, up to 10 s on a custodied signer; **quote TTL 60 s cap** (default); worst-case server hold ~70 s (cold corridor runs an on-chain decimals preflight) — **set the client timeout to 75 s** (a shorter timeout cancels nothing and discards a quote in flight). **Outstanding-RFQ cap: 4 at a time** (per API key, or per client IP keyless); a firm quote holds its slot until fill or order deadline; cancel/submit do not free it; over the cap → `429 rate_limited` with **no** `Retry-After`. Rate limit **60 requests/minute** default tier (per API key or per client IP keyless; shared IP = shared bucket), `X-RateLimit-*` headers. Errors: `400 invalid_request`, `401 unauthorized`, `403 forbidden`, `404 not_found` (someone else's RFQ is a 404, never 403), `409 conflict`, `429 rate_limited`, `502 upstream_error`, `503 venue_unavailable`, `500 internal`. Every response carries `X-Request-Id`.
- **Executing the swap:** (1) approve `takerPays` of the sell token **to `quote.reactor`** (direct taker flow) — API returns this as `transactions.approval`; USDT-style tokens reject approve(non-zero → non-zero), so reset allowance to 0 first when current allowance > 0. **Wait for the approval receipt before sending the swap** — the reactor pulls the sell token inside `executeBatch`, so broadcasting both into the same block risks the swap landing first and reverting. (2) Send `transactions.swap` from the `taker` wallet: `{to: <reactor>, data: <executeBatch calldata>, value: "0"}`. (3) Re-check the clock before broadcasting: after `expiresAt` the API rejects `/submit` and stops counting the quote; the signed order can still land until `orderDeadline`; past that it reverts. If a slow approval pushed past `expiresAt`, request a new quote — don't send. (4) Report the hash via `POST /v2/rfq/{id}/submit` (optional but recommended; fires webhooks). **Do NOT execute the top-level `encodedOrder`/`signature` directly** — when no single maker covers the size, Textile bundles several makers into one quote and `transactions.swap` is an `executeBatch` of every signed order; the top-level fields are only the first order. There is **no slippage parameter** — a firm quote is an exact signed order (`buyAmount` is what you receive, `takerPays` is what leaves); the failure mode is expiry, not a worse fill. Taker side is a **plain ERC-20 `approve` to the reactor — no Permit2 on the taker side**; Permit2 pulls the *maker's* funds.
- **Minimums:** mainnet floor is the corridor's dollar floor, default **$1 of notional** (or the feeable output plus its fee when larger; fallback 1 whole token). Below that is a 400. Testnets scale to ~$0.01. **Maximum: UNVERIFIED as a global number** — per-pair ceiling is whatever makers publish: `GET /v2/rfq/levels` returns `maxSellAmount`; above available depth returns `no_quote` with `availableSellAmount`. Treat max as live maker depth, not a fixed constant. **Live Celo corridor depth / current rates: UNVERIFIED** — not checked live for this plan; check `GET /v2/rfq/levels?chainId=42220` or `GET https://api.textilecredit.com/tickers` at build time, before promising any size.
- **Testnet / sandbox — critical:** **there is NO Celo Sepolia (or any Celo) testnet corridor.** Test keys (`tx_test_…`) work only on BSC testnet (97) and Base Sepolia (84532); pointing one at Celo Sepolia returns a 400 saying that chain has no FX settlement contract. ### 2.3 Workstream C — Self Agent ID gate

**Verified facts (sources: https://docs.celo.org/build/agents/self-agent-id, https://docs.self.xyz/docs/agent-id/overview, https://docs.self.xyz/docs/agent-id/sdk-integration, https://docs.self.xyz/docs/agent-id/register-an-agent)**

- Self Agent ID is an on-chain registry on Celo that binds an agent's signing key to a zero-knowledge proof that one real, unique human stands behind it. The agent receives a **soulbound ERC-721 NFT**; services check it with one middleware call. It implements the ERC-8004 registries (identity, reputation, validation) **plus a proof-of-human extension**. It is for verifying *agents*, not humans — for verifying humans there is a separate "Build with Self" flow.
- **A human verifies, not the agent:** the human scans their passport or ID in the Self mobile app; the ZK proof is generated on the phone and no personal data leaves the device. The Self Hub verifies the proof on Celo and calls the registry, which mints the soulbound NFT linking the agent's key to the human's unique nullifier. One human can back a bounded number of agents (default **sybil limit 1 in the verifier**; registry allows **10 per human on mainnet**, uncapped on Sepolia).
- **A programmatic check DOES exist — three ways:**
  1. **Official SDK verifier (recommended):** TypeScript SDK **`@selfxyz/agent-sdk` v0.3.1** (Node 18+), `npm install @selfxyz/agent-sdk`. The agent signs every outbound request; the service verifies with `SelfAgentVerifier` (Express middleware `verifier.auth()`, or `verifier.verify({signature, timestamp, method, url, body})` without Express). The verifier recovers the signer, reads the registry on-chain, and enforces configured rules (age, OFAC, nationality, sybil limit, replay protection, rate limit). **No API key, no central server in the path** — verification reads the on-chain registry. Defaults: sybil limit 1, replay protection on, requests older than 300 seconds rejected. Python SDK (`pip install selfxyz-agent-sdk`) and Rust (`cargo add self-agent-sdk`) also exist; all produce byte-identical signatures.
  2. **Direct on-chain read (no SDK):** require `isVerifiedAgent(agentKey)` **and** `isProofFresh(getAgentId(agentKey))`, where `agentKey = zeroPad(agentAddress, 32)`. An agent is verified when `hasHumanProof && isProofFresh`. There is also a signature-free lookup, `verifyAgent(agentKey, {network})`, returning `{verified, agentId, expiresAt}` or `{verified: false, reason: "NOT_REGISTERED" | "NO_HUMAN_PROOF" | "PROOF_EXPIRED", reauthUrl?}`.
  3. **REST API:** `https://agent-api.self.xyz` — registration and agent queries from any language, plus A2A and discovery; agent cards served at `/api/cards/{chainId}/{agentId}`. MCP server at `https://agent-api.self.xyz/api/mcp`.
- **Signing scheme:** agent signs `keccak256(timestamp + METHOD + pathWithQuery + keccak256(body))` as EIP-191 `personal_sign`, sent as headers `x-self-agent-address`, `x-self-agent-signature`, `x-self-agent-timestamp` (Ed25519 agents instead send `x-self-agent-keytype: ed25519` and `x-self-agent-key`). The signature must cover the **raw** body bytes — re-serializing parsed JSON breaks verification.
- **Contract addresses (Celo docs, stated as checked with `eth_getCode` on 2026-08-21; identity registry reports `name() = "Self Agent ID"`, `symbol() = "SAID"`):**

  | Contract | Celo mainnet (42220) | Celo Sepolia (11142220) |

  | SelfAgentRegistry (identity, proof-of-human) | `0xaC3DF9ABf80d0F5c020C06B04Cced27763355944` | `0x043DaCac8b0771DD5b444bCC88f2f8BBDBEdd379` |
  | SelfReputationRegistry | `0x69Da18CF4Ac27121FD99cEB06e38c3DC78F363f4` | see Self smart contracts |

  The reference (non-Self) ERC-8004 registries on Celo (`0x8004A169…` mainnet) are **separate contracts**; an agent can be registered in both. Do not confuse them.
- **What the check returns:** on success `req.agent` holds `address`, `agentKey`, `agentId` (bigint), `agentCount`, `nullifier` (the human's nullifier — usable to rate-limit/dedupe per human), and optionally `credentials` (nationality, `olderThan`, `ofac`, …). Failure statuses: 401 (missing/invalid headers, stale timestamp, replay, not verified on-chain, proof expired, provider mismatch, sybil over-limit, age/OFAC/nationality fail), 429 rate limit, 500 raw body unavailable, 503 chain unreadable.
- **Obtaining a Self Agent ID — step by step (verified):** prerequisites Node 18+, the Self app on a phone, a Celo RPC endpoint (`https://forno.celo.org` mainnet, `https://forno.celo-sepolia.celo-testnet.org` testnet). Full loop ~15 min per Self docs; quickstart claims ~5 min for a testnet agent.
  1. Install SDK/CLI: `npm install @selfxyz/agent-sdk` (ships the `self-agent` CLI).
  2. Start a registration session (offchain API call): `requestRegistration({mode, network, humanAddress?, disclosures})` — or CLI `self-agent register init --mode linked --human-address 0x... --network testnet`. Returns a session with `scanUrl` (embeddable QR PNG) and a deep link that opens the Self app. Default `waitForCompletion` timeout 30 min, 5 s poll interval.
  3. **Human scans the QR with the Self app (offchain, on the phone):** passport/ID scanned; ZK proof generated on the phone. **Mainnet accepts real passports/IDs only; testnet (Celo Sepolia) accepts mock documents only.** A real passport fails on Sepolia (`InvalidIdentityCommitmentRoot`); a mock passport fails on mainnet. (Third-party source only, **UNVERIFIED in official docs:** mock-passport mode is enabled by tapping the Passport button in the Self app five times — verify at build time.)
  4. Proof verified on-chain; NFT minted (onchain): Hub V2 verifies the proof on Celo and calls the registry, which mints the soulbound ERC-721 NFT binding the agent key to the human's nullifier. Session states: `initialized → handoff_opened → callback_received → onchain_verified`.
  5. Export and store the agent key: `session.exportKey()` returns the generated private key — it works only from completion until 30 minutes after, and can be re-called inside that window. Store as a secret / env var (`AGENT_PRIVATE_KEY`); never commit it. Ed25519 agents keep their own key instead.
  6. (Optional) Publish identity document: agents start with a blank `agentURI`; host an ERC-8004 registration document and have the NFT owner call `setAgentURI(agentId, url)`. `agent.setAgentCard(...)` writes the A2A agent card on-chain (NFT owner only).

Decision needed (§3, decision 2).
- **Expiry / refresh:** proofs expire at `min(document expiry, registration + 365 days)`; `isProofFresh` then becomes false. `getInfo()` exposes `proofExpiresAt` (unix seconds), `daysUntilExpiry`, `isExpiringSoon` (under 30 days). Renewal in place is via `requestProofRefresh({agentId, network})` (same agent ID and key). **⚠️ Contradiction flagged, UNRESOLVED:** the PyPI page for `selfxyz-agent-sdk` 0.2.1 says "There is no in-place refresh. Verifier and agent must be on the same network; a Celo Sepolia agent is unknown to a mainnet registry. Keep the agent host clock in sync (300 s window).
- **`https://app.ai.self.xyz` is a marketing landing page** ("Prove who's real. Human or agent."), fetched 2026-11-21 — **not** a registration console. Registration happens via the SDK/CLI/REST API + Self mobile app, not via that page.
